### 완료한 기능

- 온바탕 첫 화면과 편집기의 **내 계정 수업** → 계정 수업 목록 → 수업방 다시 열기·저장 결과를 같은 작업 영역에 연결했다. 첫 화면에서 빈 그림을 만들지 않고 편집 중에는 먼저 저장한다.
- 결과의 **원래 PPT로 결과 가져오기**에서 실제 PNG·답과 전체 자료의 쪽을 확인하고 삽입 위치를 고른다. PNG와 답을 별도 편집 요소로 추가하고 기존 쪽·앱·원본·이전 고정본을 보존한다.
- 전체 자료의 모든 파트·순서를 한 트랜잭션으로 저장한다. 용량/초안/고정본 충돌은 보호하고, 저장 응답 유실과 고정 저장 후 초안 전달 실패를 구분한다. 같은 결과 재가져오기는 막고 이미 편집한 결과를 다시 연다.
- 공통 원본의 선택적 accountAction을 가이랩에서만 연결한다. 공용의 계정·활동·앱 제작 숨김과 기존 앱·결과 실행/저장 정책은 유지한다.

### 실제 계정·실과 PPT에서 완료

1. 기존 로그인 교사 계정의 종료된 45분 수업 1개를 목록에서 열고, 학생 2명의 PNG·답이 있는 고정 결과를 조회했다. 새 계정·새 수업방을 만들지 않았다.
2. 원래 실과 PPT 전체 자료 25쪽/11파트를 출처로 찾았다. ‘19쪽 · 오늘의 활동’ 뒤를 선택해 결과를 전체 **20쪽**에 추가했고 **26쪽/11파트**가 됐다. 원본 PPT 자체는 19쪽이며 기존 앱·결과가 더해진 기기 자료가 25쪽이었다.
3. 학생 답 하나에 재편집 확인 문구를 넣고 첫 PNG 크기를 너비 19.125%에서 18.1%로 줄였다. 두 PNG의 그림 데이터는 최초 제출과 동일했다. 답과 그림을 각각 실제 편집 도구로 바꿨다.
4. **전체 자료에 저장**으로 새 고정본을 저장했다. 기준 파트 고정 버전은 17에서 19가 됐고, 서비스 전체 새로고침 후 계정 목록 → 같은 결과 → 이미 가져온 결과 편집하기로 **20/26쪽**·수정한 답·PNG 크기가 복원됐다. 고정본 비교 화면에서도 고정 버전 19와 같은 내용·크기를 확인했다.
5. 같은 결과 재가져오기는 ‘이미 전체 자료에 저장한 결과’로 막혀 중복 쪽을 만들지 않았다. 종료된 수업의 4/5단계 진행 화면을 다시 열고 편집으로 돌아와도 20/26쪽을 유지했다.
6. 서버의 최초 고정 결과 revision 1을 별도 읽기 화면에서 다시 열어 원래 답·두 PNG가 그대로임을 확인했다. 기기 재편집으로 서버 결과를 덮어쓰지 않았다.

## 운영 DB 변경 · 적용 대기

운영 main에는 기존 PR #76의 7개 Onbatang migration이 아직 없다. 이번 연결을 실제 학생에게 제공하려면 public 새 테이블 10개, private 채점 매핑 테이블 1개, 비공개 자산 bucket과 RPC/RLS가 필요하며 8번째 migration에서 slide-app/PNG/교사 쪽 동기화 계약을 더한다. **이번 세션에는 적용하지 않았다.**

`.github/workflows/supabase-deploy.yml`이 main의 `supabase/**` 변경을 자동 적용함을 확인했다. 따라서 준비 SQL을 **`docs/pending-sql/onbatang-classroom/`**에 두고 workflow와 `supabase/**`를 변경하지 않는다. 7개 기존 SQL은 원본 PR과 바이트 일치. `node scripts/prepare-onbatang-classroom-sql.mjs`는 검토용 단일 트랜잭션/해시 묶음만 만들며 DB에 연결하지 않는다. [영향 범위와 적용 조건](pending-sql/onbatang-classroom/README.md).

학생 참여 버튼은 capability를 읽기만 하여 확인한 뒤 출판한다. 서버가 없으면 원본 업로드·revision·방 쓰기 전 `SERVER_SETUP_REQUIRED`로 안내한다. 따라서 구성/교사 진행 프런트엔드는 먼저 사용할 수 있고 운영 학생 코드 활성화만 대기한다.
